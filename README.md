# ATR 自適應網格 · 台股零股每日建議系統

每天 13:00 依照持有的 ETF，算出「今天要買幾股、賣幾股」。

把兩個概念接起來：

- **網格交易**決定*方向*與*節奏* —— 跌一格買一份，漲一格賣一份。
- **ATR** 決定*格子多寬* —— 波動放大格子自動變寬，波動收斂自動變窄。
  同一套參數才能同時管得動 ATR 3% 的槓桿 ETF 和 ATR 0.4% 的債券 ETF。

而「一份」永遠固定成一件事：**手續費剛好還是 1 元的最大股數**。

---

## 一、「一份」怎麼算

國泰手續費 2.8 折、最低 1 元、元以下無條件捨去，實際費率是

```
0.001425 × 0.28 = 0.000399
```

手續費要停在 1 元，成交金額必須滿足 `floor(金額 × 0.000399) ≤ 1`，也就是

```
金額 < 2 ÷ 0.000399 = 5,012.53 元
```

所以 **一份 = floor(5012.53 ÷ 股價)** 股，隨當天股價重算：

| 標的 | 股價 | 一份 | 金額 | 手續費 | 多買 1 股 |
|---|---:|---:|---:|---:|---:|
| 富邦科技 | 61.80 | 81 | 5,005.8 | 1 元 | 2 元 |
| 統一FANG+ | 140.30 | 35 | 4,910.5 | 1 元 | 2 元 |
| 主動中信非投等債 | 10.45 | 479 | 5,005.6 | 1 元 | 2 元 |

隨時可以自己查：

```bash
atrgrid lot            # 列出所有持股
atrgrid lot 61.8 140.3 # 指定價格
```

### ⚠ 多份一定要拆單

一份的定義就是手續費 1 元的**上限**，所以兩份合併成一筆委託必然踩過門檻：

| 下單方式 | 股數 | 金額 | 手續費 |
|---|---:|---:|---:|
| 合併一筆 | 622 | 10,014 | **3 元** |
| 拆成兩筆 | 311 × 2 | 10,014 | **2 元** |

系統一律以拆單試算，報表的「下單」欄直接寫成 `2 × 311`，照著送兩筆就對了。

### 副作用：股數會慢慢累積

一份是**固定金額**（約 5,000 元）而不是固定股數，所以低點買進的股數比高點賣出的多：

```
60.35 買一份 → 83 股
61.32 賣一份 → 81 股      淨 +2 股，另外落袋現金
```

每趟往返會留下幾股。這是刻意的 —— 等同於溫和版的定額投資法，長期下來股數
緩慢增加。代價是「階數 0」不會永遠等於建檔股數，看 `atrgrid status` 時
以**階數**為準，不要用股數回推。

### 來回成本＝步長的下限依據

| 類別 | 買 | 賣 | 證交稅 | 來回成本 |
|---|---:|---:|---:|---:|
| 股票型 ETF | 1 元 | 1 元 | 0.1%（約 5 元） | **約 0.14%** |
| 債券 ETF | 1 元 | 1 元 | 免徵 | **約 0.04%** |

網格步長若沒有明顯大於這個數字，就只是在幫券商和國庫打工。
`settings.yaml` 的 `min_step_cost_multiple`（預設 3 倍）會在步長太密時發出警告。

## 二、每天 13:00 的決策流程

```
1. 取昨日以前的完整日 K            →  Wilder ATR(14)
2. 步長 = clamp(k×ATR, 下限%, 上限%)
3. 除息調整錨點 → 錨點漂移
4. (現價 − 錨點) ÷ 步長 = 幾格      →  跌破買、漲過賣
5. 六道風控閘門
6. 輸出「N 筆 × M 股」的下單建議
7. 實際成交後 → 錨點移動、階數更新
```

### 步長

```
step = clamp(atr_multiplier × ATR(14),  min_step_pct × P,  max_step_pct × P)
```

ATR 用**已收盤**的日 K 計算（今天的盤還沒收，拿來算會偷看未來）。
現價則用 13:00 的即時報價。

### 錨點（anchor）

網格的中樞。成交一份，錨點就往成交方向移動一個步長 —— 這就是網格的記憶，
存在 `state/state.json`。

兩個必要的修正：

**除息調整.** 除息當天價格自然下跌，沒調整的話網格會把除息誤判成「跌了一格」
而觸發買進。持有的高股息與債券 ETF 大多月配或季配，這個坑一定會踩到。
所以要在 `portfolio.yaml` 登記：

```yaml
ex_dividends:
  - { date: "2026-08-18", amount: 0.40 }
```

**錨點漂移.** 純網格在單邊行情會失效：一路漲會賣光後再也買不回。
所以讓錨點每天以 `drift_beta`（預設 2%）的比例往 EMA60 靠攏。

預設是 `up_only`（**只跟漲、不跟跌**）：多頭時網格跟著上移不會提早出清；
空頭時錨點不下移，避免系統性地「賣在低點」。槓桿 ETF 預設關閉漂移。

### 六道風控閘門

| 閘門 | 作用 |
|---|---|
| 代號未驗證 | `ticker_verified: false` 的標的完全不出建議 |
| 資料過期 | 日 K 超過 5 天沒更新就不出手 |
| 異常跳空 | 相對前收跳空超過 3×ATR → 轉人工複核（可能是除息、拆分或重大事件） |
| 部位上下限 | 相對建檔股數，最多加碼 `max_buy_rungs` 份、減碼 `max_sell_rungs` 份 |
| 現金上限 | 買進不得超過現金池扣除 `cash_floor` 的餘額 |
| 不賠售 | 賣出以 LIFO 配對成本，扣掉手續費與證交稅後為負就不賣 |

再加上 `max_rungs_per_day`（單日最多幾份），避免暴跌當天一次梭進去。

### 三類資產、三套參數

| | 股票型 | 債券型 | 槓桿型 |
|---|---:|---:|---:|
| ATR 倍數 | 0.8 | 1.0 | 0.7 |
| 步長下限 | 1.0% | 0.40% | 1.8% |
| 加碼上限 | 5 份 | 8 份 | **2 份** |
| 減碼上限 | 5 份 | 5 份 | **6 份** |
| 單日上限 | 2 份 | 2 份 | 1 份 |
| 錨點漂移 | up_only | up_only | **關閉** |

槓桿型刻意不對稱：**少加碼、多減碼**。正2 有長期複利耗損，往下攤平是在跟
數學作對；往上分批減碼則相對合理。

`00757 統一FANG+` 另外做了個股覆寫（步長 1.0×ATR、減碼上限 3 份）—— 已獲利
25% 的長期趨勢部位，不該被網格洗出場。

## 三、安裝與初始設定

```bash
pip install -e .          # 或 pip install -r requirements.txt
```

### 步驟 1 · 核對股票代號 ★必做★

`config/portfolio.yaml` 裡的代號是**依名稱推定**的，其中 6 檔標成 `TBD1`~`TBD6`
根本還沒填。所有標的的 `ticker_verified` 都是 `false`，這代表**系統目前一筆
建議都不會出**。

```bash
# 填好 TBD 後執行，會比對交易所登記名稱
atrgrid verify-tickers
```

全部相符後，再把各檔的 `ticker_verified` 改成 `true`。

### 步驟 2 · 設定現金池 ★必做★

`config/settings.yaml` 的 `risk.cash` 預設是 0，所有買進訊號都會被擋下。
填入實際可動用於網格加碼的金額：

```yaml
risk:
  cash: 300000
  cash_floor: 50000   # 低於這個水位就停止買進
```

現有 19 檔標的，若每檔都加碼到上限，理論最大需求約 100 萬元。實務上不會同時
發生，但現金池太小就只是每天看到「現金不足」。

### 步驟 3 · 建檔

```bash
atrgrid init
```

錨點設在**建檔當下的市價**：網格從此刻開始運作，不追溯過去的進出。

## 四、日常使用

```bash
# 每天 13:00
atrgrid advise

# 產出 HTML / Markdown
atrgrid advise --format html --out reports/today.html

# 實際成交後回填（這一步不能省，否則錨點不會移動）
atrgrid record 0052 BUY 83 60.35
atrgrid record 00757 SELL 34 143.90

# 看目前狀態
atrgrid status
```

`advise` 預設**不改變狀態**，只給建議。真正成交多少由 `record` 決定 ——
因為零股常常掛不到、或只成交部分。

### 用真實行情

```bash
atrgrid fetch --out-dir data/bars       # 從證交所下載日 K
atrgrid advise --provider twse          # 直接連線
```

### 離線試跑

repo 附了一組**合成**日 K（`data/bars/`，由 `scripts/make_demo_data.py` 產生，
不是真實行情），可以在不連網的情況下把整套流程跑一遍：

```bash
atrgrid advise --provider csv --csv-dir data/bars --price 0052=60.35
```

## 五、回測

回測的用途不是預測賺多少，而是**檢查參數合不合理**：一年成交幾次？成本吃掉
多少？部位會不會撞到上下限而長期停擺？

```bash
atrgrid backtest 0052 00725B --provider csv --csv-dir data/bars
atrgrid backtest 0052 --sweep    # 掃描不同 ATR 倍數
```

留意輸出裡的「**觸頂 N 日**」：那是網格加碼到上限後停擺的天數。數字太大代表
`max_buy_rungs` 或步長需要調整 —— 也代表那段期間網格幫不上忙。

## 六、自動化

`.github/workflows/daily-advice.yml` 每個交易日 13:00（台北）跑一次，把報表
貼在 Actions 的 Job Summary，並把更新後的狀態 commit 回 repo。

要收到通知的話，在 repo 設定 `NOTIFY_WEBHOOK` secret（Discord / Slack 都可以）。

## 七、這套系統不做什麼

講清楚比較好：

- **不會自動下單。** 只產生建議，實際委託由你自己送。
- **不判斷基本面。** 網格假設價格會在區間內來回。單邊趨勢中它會表現得很差 ——
  下跌時一路買到撞上限，上漲時一路賣到撞下限。部位上下限是**傷害控制**，
  不是獲利來源。
- **不管資產配置。** 19 檔標的的權重是否合理、債券部位是否過重，系統不會有意見。
- **不處理稅務與股利再投資。**

網格適合震盪、不適合趨勢。這套系統把 ATR 拿來讓格子隨波動呼吸、把部位上下限
拿來限制單邊行情的傷害，但改變不了這個本質。

## 專案結構

```
config/
  settings.yaml       全域參數（手續費、三類資產的網格參數、風控）
  portfolio.yaml      持股清單 ★代號待驗證★
src/atrgrid/
  fees.py             手續費 / 證交稅 / 「一份」股數
  indicators.py       Wilder ATR、EMA
  engine.py           網格引擎與風控閘門
  state.py            錨點、階數、成本批次的持久化
  data.py             證交所 / CSV 行情來源
  backtest.py         參數檢查用回測
  report.py           終端機 / Markdown / HTML 報表
  cli.py              指令入口
state/state.json      網格記憶（會被自動更新，建議進版控）
tests/                93 個測試
```
